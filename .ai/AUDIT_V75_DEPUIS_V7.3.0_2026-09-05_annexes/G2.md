## Constats (du plus grave au moins grave)

### [P0] `KillSourceDecoderRev` figé alors que le décodeur a changé : les morts des matchs à véhicule gardent la lecture d'avant la correction, et aucun chemin ne les redécodera

- **Où** : `apps/go-api/internal/sync/killcollector/collector.go:65`
  (`const KillSourceDecoderRev = "killsource-2026-07-31"`) ;
  prédicat de reprise `apps/go-api/internal/sync/killcollector/postsync.go:369-377`
  (`... AND e.decoder_rev = ? AND e.read_path <> ?`, args ligne 397) ;
  même prédicat côté CLI `apps/go-api/cmd/levelup/cmd_backfill_killsource.go:403`.
- **Règle enfreinte** : le contrat écrit sur la constante elle-même —
  `collector.go:60-64` : « *c est elle qui permettra de savoir QUELS matchs redecoder apres un
  changement de decodage… **LA FAIRE EVOLUER a chaque changement de decodage qui change les
  lignes produites** * » ; et anti-pattern nº9 de CLAUDE.md, « **Doc inversée** — la doc … se met
  à jour dans le commit qui bascule le défaut » (ici la doc *machine* du décodage, celle sur
  laquelle la reprise s'appuie, n'a pas été mise à jour dans le commit qui a changé le décodage).
- **Conséquence** : le merge d'intégration `328d83232` déclare noir sur blanc, harnais
  d'équivalence à l'appui : « `killsource` bouge sur ces 4 films et sur EUX SEULS. Ce dernier écart
  est la CORRECTION DECLAREE du lot V9 … le kill-feed des matchs à véhicules **change dans le sens
  de la correction** ». L'étape observée est bien `killsource.Decode` (`replaybuild/replaybuild.go:332`,
  `b.observe("killsource", ksRes)`). Les lignes déjà en base pour ces matchs portent
  `decoder_rev = 'killsource-2026-07-31'`, exactement la valeur courante : le prédicat de backlog
  les EXCLUT à vie, et le CLI aussi sauf `--force` (qui redécode tout le corpus, 3 à 11 h).
  `match_kill_events_latest` est lue par ~21 fichiers de production — dont
  `platform/duckdb/killsource_weapon_kills_repo.go` (arme du kill servie sur la fiche de match et
  la carrière), `domain/match_view_kill_distance.go`, `domain/assist_pairs.go`. Sur les matchs à
  véhicule (BTB), la source du dégât fatal, la catégorie et l'assistant restent ceux de la lecture
  fausse, **servis**, sans qu'aucun compteur ne bouge. Aucun garde-rail n'existe pour lier la
  constante au paquet décodeur (14 commits sur `internal/games/halo_infinite/film/killsource/`
  depuis `v7.3.0`, 0 bump de la constante depuis sa création).
- **Reproduction** :
  `git log --oneline v7.3.0..HEAD -- apps/go-api/internal/games/halo_infinite/film/killsource/ && git log -G'KillSourceDecoderRev = ' --oneline v7.3.0..HEAD -- apps/go-api/internal/sync/killcollector/collector.go`
  (14 commits à gauche, 0 à droite).
- **Traitement proposé (v2)** : bumper la révision dans le commit qui a changé le décodage et
  poser le garde-rail qui manque — un test qui hache le contenu non-test de
  `games/halo_infinite/film/killsource/` + des désérialiseurs `filmdec` dont il dépend, et exige
  que `KillSourceDecoderRev` change quand l'empreinte change (même dispositif que
  `replaySchemaLogic.guard.test.ts` ou le garde G1 de la table ECS). Une révision par famille
  de lignes produites (kills / shots / positions) plutôt qu'une par producteur.

## Vue d'ensemble pour une v2

1. **Un fait, un producteur, une horloge de version.** Le kill est décodé deux fois du même film
   (1.57 en base, 1.58 dans l'artefact) sous deux versionnages sans lien. Cible : `killsource.Decode`
   appelé UNE fois par match, son `Result` alimentant à la fois la passe DuckDB et l'artefact —
   et une seule constante de révision par famille de lignes, tenue par un garde-rail d'empreinte.
2. **Le stockage canonique par fait.** Kills/positions de kill → tables append-only + `_latest`
   (déjà juste). Positions complètes, score, objectifs, équipement, bombe → **l'artefact** est le
   modèle de calcul ; les tables (`match_usage_*`, `match_bomb_stats`, `real_start_time`) sont des
   *projections* de l'artefact. `match_objective_events` doit choisir : soit elle devient une
   projection comme les autres (et son écrivain DELETE-then-INSERT disparaît), soit elle est
   retirée avec l'endpoint et les deux calques web qu'elle n'alimente pas.
3. **Le moment.** Les projections se déclenchent sur « un artefact vient d'être RANGÉ », pas sur
   « ce cycle a cuit » — donc aussi bien après `StoreBuildArtifact` (ouvrier) qu'après `buildAll`
   (local). C'est le seul changement qui rend les statistiques d'Assaut et le bloc usage vivants
   en production.
4. **Le rattrapage est un composant, pas un copier-coller.** 1.57 et 1.58 ont chacun réécrit
   « queue récente bornée + marqueur terminal + budget » ; les projections n'en ont aucun. Un seul
   `backlog.Selectionner(source, predicat, horizon, plafond)` pour les quatre, avec le prédicat de
   fraîcheur *unique* (le digest).
5. **Ajouter un calque, en v2** : un fichier `layer_<nom>.go` qui déclare
   `{nom, requiert, produit, scan, document, coverage}` ; l'ordonnanceur trie, `document.go` ne
   bouge plus, `coverage.go` non plus, et la version de schéma servie n'est touchée que si le
   *contrat API* change — pas si un champ interne s'ajoute.

## Axe H — `PlotOptions` dataclass

### Problème

La quasi-totalité des 150 `# noqa: PLR0913` dans `src/visualization/` vient des fonctions
`plot_*` qui transportent individuellement `lang`, `smooth`, `height`, `colors`, `show_record`,
`n_players`, `labels`, `is_inverse`, etc. Chaque ajout de paramètre de style = +1 violation.

Exemples typiques :
```python
def plot_trio_metric(series, metric, records, colors_by_name,
                     player_names, n_players, lang="fr",
                     smooth=False, height=360, ...):  # noqa: PLR0913

def plot_map_perf_vs_history(df, player, colors, lang="fr",
                              height=400, show_smooth=True, ...):  # noqa: PLR0913
```

### Solution

Créer `src/visualization/_plot_options.py` :

```python
@dataclass
class PlotOptions:
    """Paramètres de style/présentation communs aux graphes."""
    lang: str = "fr"
    smooth: bool = False
    height_px: int = 360
    show_records: bool = True
    is_negative: bool = False  # axe Y inversé (morts, etc.)

    @classmethod
    def from_session(cls) -> "PlotOptions":
        """Construit depuis get_lang() — seul point de contact UI."""
        from src.ui.i18n import get_lang
        return cls(lang=get_lang())
```

Adoption progressive : ajouter `opts: PlotOptions = PlotOptions()` aux fonctions les plus
violatrices, les paramètres individuels restent en **legacy** avec `# LEGACY` jusqu'à migration
complète des appelants.

**Fichiers prioritaires :**

| Fichier | Violations PLR0913 actuelles |
|---------|------------------------------|
| `src/visualization/_perf_progression.py` | 3 fonctions à 6-8 params |
| `src/visualization/timeseries.py` | 4 fonctions |
| `src/visualization/trio.py` | 2 fonctions |
| `src/visualization/maps_outcome.py` | 2 fonctions |
| `src/visualization/match_bars.py` | 2 fonctions |

**Gain attendu :** suppression de ~80-100 des 250 `# noqa` dans viz.

## Axe I — `render_chart_or_info` helper

### Problème : deux patterns coexistent, l'un est risqué

Toutes les fonctions `plot_*` peuvent retourner `None` si les données sont insuffisantes.
Ce `None` n'est pas toujours vérifié avant `st.plotly_chart` :

```python
# Pattern A — correct (timeseries.py, teammates_charts.py)
with safe_chart_render():
    fig = plot_something(data)
    if fig is not None:
        st.plotly_chart(fig, width="stretch", config=PLOTLY_CLEAN_CONFIG)
    else:
        st.info(t("insufficient_data_chart"))

# Pattern B — risqué (win_loss.py, career.py, match_view_charts.py, _session_compare_viz.py...)
fig = plot_something(data)
st.plotly_chart(fig, ...)  # AttributeError si fig=None, pas de message utilisateur
```

**Conséquence** : sans `safe_chart_render`, une figure `None` lève une exception visible dans
l'UI. Avec `safe_chart_render`, elle est absorbée silencieusement → le graphe disparaît sans
explication. Ni l'un ni l'autre n'est satisfaisant.

### Solution : helper `render_chart_or_info`

```python
# Dans src/ui/chart_utils.py
def render_chart_or_info(
    fig: go.Figure | None,
    *,
    key: str,
    config: dict = PLOTLY_CLEAN_CONFIG,
    info_key: str = "insufficient_data_chart",
) -> None:
    """Affiche un graphe ou un message si fig=None. Toujours dans safe_chart_render."""
    with safe_chart_render():
        if fig is not None:
            st.plotly_chart(fig, width="stretch", key=key, config=config)
        else:
            st.info(t(info_key))
```

Remplace le Pattern A boilerplate par un appel unique. Le Pattern B disparaît.

### Pages à migrer (Pattern B actif)

| Fichier | `st.plotly_chart` sans garde `None` |
|---------|-------------------------------------|
| `win_loss.py` | ~10 appels |
| `career.py` | ~3 appels |
| `career_lusr.py` | 1 appel |
| `match_view_charts.py` | ~2 appels |
| `match_view_participation.py` | ~2 appels |
| `_session_compare_viz.py` | ~3 appels |
| `objective_analysis.py` | ~4 appels |
| `teammates_map_charts.py` | ~8 appels |

**Note** : les 58 `with safe_chart_render` existants sont en place. L'objectif est d'uniformiser
le traitement `None` + de supprimer les blocs `if fig is None` inline en faveur du helper.

## Axe J — `BaseService` interface commune

### Problème

Les 5 services (`WinLossService`, `TeammatesService`, `TimeseriesService`,
`FilmStartService`, `WeaponExtractionService`) ont chacun leur propre `__init__` sans contrat
commun. Ajouter un 6e service signifie réinventer le pattern.

### Solution

Créer `src/data/services/_base.py` :

```python
from __future__ import annotations
from dataclasses import dataclass, field
from src.data.repositories.duckdb_repo import DuckDBRepository


@dataclass
class BaseService:
    """Contrat minimal pour tous les services de données."""
    db_path: str
    db_key: tuple[int, int] | None = None

    def make_repo(self) -> DuckDBRepository:
        """Instancie un repo frais (à utiliser dans un context manager)."""
        return DuckDBRepository(self.db_path, db_key=self.db_key)
```

Migration : faire hériter les services existants de `BaseService`.
Non invasif — les méthodes métier ne changent pas.

**Note :** `WeaponExtractionService` a un profil différent (async, IO intensive) — l'héritage
est optionnel pour celui-ci.

## Axe K — Clés `session_state` typées

### Problème

~50 string-keys `st.session_state` éparpillées dans `src/app/`, `src/ui/`, `streamlit_app.py`.
Une typo ou un renommage partiel crée un bug silencieux : la clé n'existe pas → `None` →
comportement inattendu sans exception.

Exemples de clés actuelles :
```
"filter_maps", "_playlists_exclusions", "_pending_filter_mode",
"filter_experience_types", "_filters_loaded_*", "_filter_mode_shadow", ...
```

### Solution

Créer `src/app/session_keys.py` :

```python
class SK:
    """Clés canoniques de st.session_state. Usage : st.session_state[SK.FILTER_MAPS]"""

    # Filtres cascade
    FILTER_MAPS = "filter_maps"
    FILTER_MODES = "filter_modes"
    FILTER_PLAYLISTS = "filter_playlists"
    FILTER_EXPERIENCE_TYPES = "filter_experience_types"

    # Intent-based (mode + exclusions)
    MAPS_FILTER_MODE = "_maps_filter_mode"
    MAPS_EXCLUSIONS = "_maps_exclusions"
    MODES_FILTER_MODE = "_modes_filter_mode"
    MODES_EXCLUSIONS = "_modes_exclusions"
    PLAYLISTS_FILTER_MODE = "_playlists_filter_mode"
    PLAYLISTS_EXCLUSIONS = "_playlists_exclusions"

    # Shadows (robustesse Streamlit 1.54+)
    FILTER_MODE_SHADOW = "_filter_mode_shadow"
    START_DATE_SHADOW = "_start_date_cal_shadow"
    END_DATE_SHADOW = "_end_date_cal_shadow"

    # Pending states
    PENDING_FILTER_MODE = "_pending_filter_mode"
    PENDING_SESSION_LABEL = "_pending_picked_session_label"

    # Debug
    SHOW_DEBUG_INFO = "_show_debug_info"
```

Migration : remplacement `"filter_maps"` → `SK.FILTER_MAPS` fichier par fichier.
Grep de validation : `grep -rn '"filter_maps"\|"filter_modes"\|"filter_playlists"' src/`
doit retourner 0 après migration complète.

**Gain** : IDE détecte les typos, grep centralisé, renommage trivial.

## Axe L — Résorber C901/PLR0912 restants

### Problème

76+ fonctions avec `# noqa: C901` (complexité cyclomatique > 12) dans `src/`.
Ces fonctions sont non-testables en isolation et fragiles aux changements.

### Méthode

Pour chaque fonction violatrice :
1. Identifier les branches indépendantes (chaque `if/elif` sur un type différent)
2. Extraire en sous-fonctions nommées à responsabilité unique
3. La fonction principale devient un dispatcher de 5-8 lignes

**Cibles prioritaires (les plus grosses) :**

| Fonction | Fichier | Violations |
|----------|---------|-----------|
| `apply_filters` | `_filters_apply.py` | C901 + PLR0912 + PLR0915 |
| `_add_derived_columns` | `_filters_apply.py` | C901 + PLR0912 (partiellement résorber en Axe D) |
| `render_match_impact_section` | `match_view_players.py` | PLR0912 + PLR0913 |
| `_compute_all_filter_options` | `filters_render.py` | — |

**Note :** `apply_filters` perdra 2 violations PLR0913 après Axe D (suppression de
`_add_derived_columns` qui absorbe 2 callbacks). Lancer Axe D avant Axe L sur ce fichier.

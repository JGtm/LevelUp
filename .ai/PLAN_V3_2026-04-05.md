## Axe H — `PlotOptions` + `ChartTheme`

### Contexte dans le pipeline graphe

V3 complète les deux couches manquantes du pipeline instauré en V1/V2 :

| Couche | V1/V2 | V3 Axe H |
|--------|-------|----------|
| **Chart Model** | `ChartData` / `SquadRecordSet` — quelles données | — déjà en place |
| **Options** | — | `PlotOptions` — comment les styler (layout, smooth, height) |
| **Thème** | — | `ChartTheme` — couleurs sémantiques découplées des données |
| **Render** | — | `render_chart_or_info` (Axe I) — acte de rendu safe et uniforme |

### Problème — `PlotOptions`

Les violations PLR0913 concernent à la fois `src/visualization/` ET `src/ui/components/` et
`src/ui/pages/` : les fonctions chart transportent individuellement `lang`, `smooth`, `height`,
`colors`, `fill_opacity`, `line_width`, etc. `src/ui/` n'avait pas été audité initialement —
83 violations PLR0913/C901 y sont présentes. Les fonctions de type chart (radar, gauge,
annotations) sont éligibles à `PlotOptions` ; les fonctions de rendu UI complexes vont en Axe L.

Exemples typiques :
```python
def plot_trio_metric(series, metric, records, colors_by_name,
                     player_names, n_players, lang="fr",
                     smooth=False, height=360, ...):  # noqa: PLR0913
```

### Problème — `ChartTheme`

Les couleurs sémantiques sont éparpillées en 5 endroits distincts avec des incohérences :
- `PERFORMANCE_COLORS` dans `_perf_cumulative.py`
- `OBJECTIVE_COLORS` dans `objective_charts_extra.py`
- `LEAD_MY_BG` / `LEAD_ENEMY_BG` dans `_team_dominance_helpers.py`
- `avg_color = "rgba(255,255,255,0.55)"` inline dans `trio.py`
- `annotation_color = "#E69F00"` / `"#ffaa00"` — deux valeurs proches pour la même chose

Les paramètres visuels des records (pattern hachuré) sont des magic numbers dans
`_squad_record_shapes.py`. Aucun endroit unique pour changer le style global.

### Solution — `_plot_options.py` (< 120L)

```python
from __future__ import annotations
from dataclasses import dataclass, field
from src.config import HALO_COLORS, OKABE_ITO_PALETTE, THEME_COLORS


@dataclass
class ChartTheme:
    """Thème visuel global — découplé des données, modifiable en un point.

    DEFAULT_THEME est le singleton utilisé par PlotOptions.
    Modifier DEFAULT_THEME = tous les graphes migrent immédiatement.
    """
    # Fond et texte (hérite de ThemeColors)
    bg_plot: str = field(default_factory=lambda: THEME_COLORS.bg_plot_rgba(1.0))
    font_color: str = field(default_factory=lambda: THEME_COLORS.text_primary)
    grid_color: str = "rgba(255,255,255,0.07)"
    border_color: str = field(default_factory=lambda: THEME_COLORS.border)

    # Joueur solo et palette escouade
    solo_color: str = field(default_factory=lambda: HALO_COLORS.cyan)
    squad_palette: list[str] = field(default_factory=lambda: list(OKABE_ITO_PALETTE))

    # Sémantique performance
    color_positive: str = field(default_factory=lambda: HALO_COLORS.green)
    color_negative: str = field(default_factory=lambda: HALO_COLORS.red)
    color_kills: str = "#009E73"      # vert bleuté Okabe-Ito
    color_deaths: str = "#D55E00"     # vermillon Okabe-Ito
    color_kd: str = "#E69F00"         # orange Okabe-Ito
    color_baseline: str = "#999999"   # gris neutre
    color_rolling: str = "#CC79A7"    # rose mauve Okabe-Ito
    color_trend_up: str = "#009E73"
    color_trend_down: str = "#D55E00"

    # Valeurs de référence visuelles
    avg_color: str = "rgba(255,255,255,0.55)"    # moyenne, courbe lissée
    avg_dash: str = "dot"
    baseline_color: str = "rgba(255,255,255,0.35)"  # ligne zéro
    annotation_color: str = "#E69F00"            # records, highlights (unifié)

    # Records — barres fantômes hachurées (_squad_record_shapes.py)
    record_pattern_shape: str = "/"
    record_pattern_opacity: float = 0.55
    record_pattern_size: int = 8
    record_pattern_solidity: float = 0.35
    record_border_width: float = 2.0

    # Axe zéro (ligne gras blanc sur graphes K/D, trio, combat)
    zero_line_color: str = "rgba(255,255,255,0.75)"
    zero_line_width: int = 2

    # Zones win/loss (fond coloré)
    zone_win_bg: str = "rgba(0,158,115,0.22)"
    zone_loss_bg: str = "rgba(213,94,0,0.22)"


DEFAULT_THEME = ChartTheme()  # singleton — modifier ici = tous les graphes migrent


@dataclass
class PlotOptions:
    """Paramètres de présentation d'un graphe — découplés des données."""
    lang: str = "fr"
    smooth: bool = False
    height_px: int = 360
    show_records: bool = True
    is_negative: bool = False       # axe Y inversé (morts, etc.)
    theme: ChartTheme = field(default_factory=lambda: DEFAULT_THEME)

    @classmethod
    def from_session(cls) -> "PlotOptions":
        """Construit depuis get_lang() — seul point de contact UI."""
        from src.ui.i18n import get_lang
        return cls(lang=get_lang())
```

## Axe I — `render_chart_or_info` helper

### Problème : deux patterns coexistent, l'un est risqué

Toutes les fonctions `plot_*` peuvent retourner `None` si les données sont insuffisantes.
Ce `None` n'est pas toujours vérifié avant `st.plotly_chart` :

```python
# Pattern A — correct (timeseries.py, teammates_charts.py)
with safe_chart_render():
    fig = plot_something(data)
    if fig is not None:
        st.plotly_chart(fig, width="stretch", config=PLOTLY_CLEAN_CONFIG)
    else:
        st.info(t("insufficient_data_chart"))

# Pattern B — risqué (win_loss.py, career.py, match_view_charts.py, _session_compare_viz.py...)
fig = plot_something(data)
st.plotly_chart(fig, ...)  # AttributeError si fig=None, pas de message utilisateur
```

**Conséquence** : sans `safe_chart_render`, une figure `None` lève une exception visible dans
l'UI. Avec `safe_chart_render`, elle est absorbée silencieusement → le graphe disparaît sans
explication. Ni l'un ni l'autre n'est satisfaisant.

### Solution : helper `render_chart_or_info`

```python
# Dans src/ui/chart_utils.py
def render_chart_or_info(
    fig: go.Figure | None,
    *,
    key: str,
    config: dict = PLOTLY_CLEAN_CONFIG,
    info_key: str = "insufficient_data_chart",
) -> None:
    """Affiche un graphe ou un message si fig=None. Toujours dans safe_chart_render."""
    with safe_chart_render():
        if fig is not None:
            st.plotly_chart(fig, width="stretch", key=key, config=config)
        else:
            st.info(t(info_key))
```

Remplace le Pattern A boilerplate par un appel unique. Le Pattern B disparaît.

### Pages à migrer (Pattern B actif)

> **Note d'audit :** `win_loss.py`, `career.py`, `match_view_participation.py` et
> `teammates_map_charts.py` sont **déjà conformes** (safe_chart_render + if fig is not None partout).
> Ils ont été retirés de la liste. Les cibles ci-dessous ont été vérifiées et ont de vraies anomalies.

| Fichier | Anomalie confirmée |
|---------|-------------------|
| `career_lusr.py` | 1 appel sans garde `None` |
| `match_view_charts.py` | ~2 appels dans `safe_chart_render` sans `if fig is not None` |
| `_session_compare_viz.py` | 1 appel ligne ~365 sans garde (reste du fichier déjà correct) |
| `objective_analysis.py` | 1 appel (`fig_pie` ligne ~244) sans aucune garde |
| `session_compare.py` | à vérifier ligne ~384 |
| `session_compare_charts.py` | à vérifier lignes ~146, ~373, ~493 |
| `match_view_players_timeline.py` | à vérifier lignes ~124, ~168 |

**Contrainte implémentation :** `render_chart_or_info` exige un paramètre `key: str` unique par

collisions (deux graphes sur la même page ne peuvent pas partager la même clé).

**Note** : les 89 `with safe_chart_render` existants sont en place. L'objectif est d'uniformiser
le traitement `None` + de supprimer les blocs `if fig is None` inline en faveur du helper.

## Axe J — `ServiceProtocol` contrat minimal

### Problème

Les services `WinLossService`, `TeammatesService`, `TimeseriesService` sont **stateless** :
leurs méthodes sont des `@staticmethod`, `db_path` est passé en argument à chaque appel.
Il n'y a pas de `__init__` à contractualiser. Ajouter un 4e service stateless signifie
réinventer le même pattern sans guide.

> **Pourquoi pas `BaseService(dataclass)` ?**
> L'approche initiale du plan supposait des services à instances avec `self.db_path`.
> Refactoriser les 3 services stateless en services stateful changerait toute leur API
> et obligerait à mettre à jour tous les call-sites UI. Effort réel : ~1 journée, non ~1h.
> `FilmStartService` et `WeaponExtractionService` ont des profils encore plus divergents
> (connexion injectée, async) — ils restent hors scope.

### Solution

Créer `src/data/services/_base.py` avec un `Protocol` léger :

```python
from typing import Protocol
from src.data.repositories.duckdb_repo import DuckDBRepository


class StatelessServiceProtocol(Protocol):
    """Contrat documentaire pour les services stateless (méthodes @staticmethod).
    
    Usage : les services conformes n'héritent pas, ils satisfont structurellement
    le protocole (duck typing). Ce Protocol sert de documentation et de type-hint.
    """

    @staticmethod
    def make_repo(db_path: str, xuid: str | None = None) -> DuckDBRepository:
        """Instancie un repo frais pour un appel donné."""
        ...
```

Chaque service existant expose déjà une `make_repo` ou équivalent. Le Protocol ne change
aucune implémentation — il formalise le pattern pour les nouveaux services.

**Note :** `FilmStartService` et `WeaponExtractionService` gardent leur pattern actuel
(injection de dépendances via `__init__`) ; ils ne satisfont pas ce Protocol et c'est voulu.

# NOTE 5.21 — LE BLOC DE TYPE 1 : LA TABLE DE DATUMS DU CHUNK

Lot 5.21, branche `feat/decfilm-71`, base `f0352e6bf` (lots 5.1 a 5.20, grammar-2026-09-22.8,
schema 67). Sur la decouverte D1 du lot 5.20 : « le bloc de type 1 est la table de datums du
chunk, son `+4` est l archetype, c est la seule source `slot -> archetype` qui reste apres que
l image-cle a ete mesuree a 0,0 % ». La premiere moitie est vraie ; **la seconde est fausse, et
la mesure le dit**.

## 1. LE LECTEUR, CHEZ L ECRIVAIN

Le bloc de type 1 n est pas consomme par la pompe de lecture courante — `FUN_142989418` lit
seize octets et avance un compteur, ce que le 5.16 §2.2 (c) avait pris pour « le bloc est
saute ». Il est consomme par le **chemin de chargement d etat**, juste avant l image-cle :

```
FUN_1428e2aab4 :                                   ; le conteneur, AVANT toute lecture
    FUN_1408be284(local_88)                        ; un conteneur de datums NEUF
    pour chaque entree, pas 0x18 : *(entree + 4) = 1   ; <- LA PRE-INSCRIPTION
    local_88[8] = 0 ; local_88[9] = 0 ; *(u32 *)(local_88 + 10) = 0   ; la queue a zero
    FUN_1428e2a04(&DAT_144c23178)                  ; LIT LE BLOC DE TYPE 1 PUIS L IMAGE-CLE
    FUN_142f22be8(monde + 0x120, local_88)         ; applique au monde

FUN_1428e2a04(session) -> FUN_1428e2a9c(session, _, enTete, ctx, tableau) :
    FUN_1429883ec(session+0x130, enTete, *(ctx + 0x40))   ; LE BLOC DE TYPE 1
    FUN_142988338(session+0x130, hdr2, 0x10, 0)           ; l en-tete de l image-cle
    FUN_142988338(session+0x130, session[0x240], hdr2.taille, 0)
    FUN_1424c7b4c(lecteur, session[0x240], taille)
    FUN_142e2bfd0(lecteur, tableau)                       ; L IMAGE-CLE (lot 5.20)
```

`FUN_1429883ec`, bit par bit (decompilation + desassemblage ; `MOV R8,RBX` au site d appel de
`FUN_14297ea84`, `MOV byte ptr [RBX+0x1],DL`, `MOV dword ptr [RBX+0x4],EDX`, `LEA R8,[RBX+0x8]`,
`ADD RBX,0x18`) :

```
FUN_1429907c8(tampon, bitmapOctets + 0x14 + nEntrees * 0x18)   ; reserve, pas la taille lue
FUN_142988338(session, tampon, enTete.taille, 0)               ; LE BLOC ENTIER
FUN_1424c7b4c(lecteur, tampon, taille) ; FUN_1406d5cc0(lecteur, 3)   ; 0 bit consomme
pour e de table[0] a table[1], pas 0x18, borne par DAT_144706100 :
    FUN_14297ea84(lecteur, _, e+0x00)   ; R(6)                 -> drapeaux
    R(8)                     -> e+0x01                         -> generation (tag de l eid)
    R(32)                    -> e+0x04                         -> COMPTEUR DE GENERATION
    FUN_140e74e6c(lecteur, _, e+0x08)   ; 33 x R(1), LSB d abord -> masque par vue
pour b de table[4] a table[5], pas 0x20, borne par DAT_144706100 :
    0x100 x R(1), LSB d abord dans huit mots de 32 bits        -> MASQUE DE COMPOSANTS
pour q de table+0x40 a table+0x54, pas 4 :
    R(32)                                                      -> cinq compteurs du magasin
```

Les deux largeurs que `FUN_1429883ec` ne montre pas se lisent chez ses appeles :
`FUN_14297ea84` prend les **six** bits de tete de sa fenetre (`octet de tete >> 2`) et les ecrit
en un octet ; `FUN_140e74e6c` boucle **`0x21` = 33** fois sur `FUN_1406cf008` en posant `1L << i`.
`FUN_140e74b74` parcourt la meme table `i < 0x21` : ce sont les **33 vues**.

`table` est `monde+0x120` : `FUN_1408f1618` dimensionne `+0x120`/`+0x128` (pas `0x18`) et
`+0x140`/`+0x148` (pas `0x20`) AU MEME CARDINAL, et `+0x160` porte les cinq mots.

## 2. LA GRAMMAIRE EST FERMEE PAR L ARITHMETIQUE, PUIS PAR LA MESURE

```
par slot      6 + 8 + 32 + 33 = 79 bits, + 256 bits de masque = 335
8 191 slots   8 191 x 335                    = 2 743 985 bits
queue         5 x 32                         =       160 bits
TOTAL                                        = 2 744 145 bits = 343 019 octets (7 de bourrage)
```

343 019 est la taille **CONSTANTE** mesuree du bloc sur les deux films (5.20.3 (d)), et 8 191 est
`DAT_144706100`. Le decoupage n est pas choisi : `2 743 985 = 5 x 67 x 8 191`, et `8 191 x 335`
est le seul facteur qui rende une entree plausible.

**GATE (i) : 32 blocs sur 32 fermes** (5 sur `dad793c7`, 27 sur `bfecd02b`), 8 191 entrees
chacun, 2 744 145 bits lus, 7 bits de bourrage, 0 erreur.

## 3. CE QUE LE BLOC PORTE — ET CE QU IL NE PORTE PAS

### 3.1 `+0x04` N EST PAS L ARCHETYPE : D1 (5.20) EST CORRIGE

Trois classes d entree sur les 221 157 entrees de `bfecd02b`, et deux de plus, marginales :

| drapeaux | generation (`+0x01`) | `+0x04` | `bfecd02b` | `dad793c7` |
|---|---:|---:|---:|---:|
| `0x0` (jamais allouee) | 0 | **1** | 190 043 | 40 016 |
| `0x0` (liberee, trace gardee) | 1 | **2** | 18 360 | 19 |
| `0x5` (**vivante**) | 1 | **2** | 12 681 | 920 |
| `0x0` | 2 | **3** | 63 | 0 |
| `0x7` (allouee + liberee + publiee) | 1 | **2** | 6 | 0 |
| `0x5` (vivante, 2e generation) | 2 | **3** | 4 | 0 |

`+0x04` vaut **TOUJOURS `+0x01 + 1`** : c est le compteur de generation du slot, dont `+0x01` ne
garde que les deux bits de tete de l eid. Et `FUN_142e2aab4` l a pre-inscrit a `1` dans tout le
conteneur AVANT la lecture. Un archetype prendrait des dizaines de valeurs sans rapport avec la
generation ; celui-ci en prend trois. `FUN_142f30610` lit bien `datum+4` pour ecrire l en-tete
d une entree d image-cle, mais il le lit dans la table du **monde vivant** au moment de
l ecriture — pas dans ce conteneur-ci, qui est le point de DEPART du chunk.

Les drapeaux, eux, sont confirmes : le predicat complet de `FUN_1408f1730`
(`(f & 1) && (f & 4) && !(f & 2) && !(f & 0x20)`) retient exactement la classe `0x5`, et
`FUN_1408f12c4` (`|= 2`) explique la classe `0x7`.

### 3.2 LE BITMAP DE 256 BITS EST LE MASQUE DE PRESENCE DES COMPOSANTS

Sous l archetype que l image-cle donne au slot, **chaque bit leve tombe dans les bornes de la
liste de composants de cet archetype, et le nomme** :

| slot | `ti` | composants | bits leves |
|---:|---:|---:|---|
| 1 | 34 | 17 | `tacmap-cameraheading`, `tacmap-fasttravelstate`, `tacmap-waypointstate`, `tacmap-queuedreplaymission` |
| 2 | 2 | 18 | treize composants `game-engine-*` |
| 3 a 12 | 6 | 58 | `{3, 5, 7, 13, 15, 57}` — **le MEME masque pour les dix** |

**ZERO bit hors bornes** sur les 32 blocs des deux films (2 842 bits leves sur le seul chunk 22
de `bfecd02b`). C est le meme masque que celui d un record, et il est **constant par
archetype** : 184 masques distincts pour 2 ambigus sur `bfecd02b`, 22 pour 2 sur `dad793c7`.

### 3.3 LES CINQ MOTS DE QUEUE SUIVENT LE MAGASIN

`bfecd02b`, chunks 1 -> 27 : `[123 0 777 0 1581]` … `[124 603 780 1048 2645]`. Trois des cinq
croissent avec le chunk ; `dad793c7` les fige a `[124 513 0 0 1346]`. Ce sont des compteurs du
magasin de datums, non requis par ce lot et non instrumentes au-dela du journal.

## 4. LA LIAISON, ET POURQUOI ELLE NE FERME AUCUN PAQUET

L ordre du jeu est : conteneur vierge, bloc de type 1, image-cle qui ECRASE, application au
monde. Hors ligne l ordre s inverse, parce que le bloc ne NOMME pas les archetypes : l image-cle
d abord (elle nomme), le bloc ensuite (il complete par le pont `masque -> archetype`, un masque
ambigu ne liant rien). Le contenu de la table est le meme ; seule la fabrication differe.

Le bloc est la lecture **exhaustive et non heuristique** de la table de datums du chunk : il
confirme le balayeur d ancres au slot pres (479 contre 479 sur le chunk 22) au lieu de
l etendre. **D1 (5.20) est referme des deux bouts** : la naissance que le residu attend n est ni
dans l image-cle du chunk (0,0 %, 5.20.2) ni dans sa table de datums (0 %, ici). Elle est APRES
le debut du chunk, dans le flux de trame, et le 5.19 §D1 avait deja mesure que le chunk 2 lit
ZERO `NEW` sur 1 196 paquets alors qu au moins dix entites y naissent : **c est la lecture du
record `NEW` du flux, pas une troisieme table, qu il faut reprendre.**

par chunk pour poser zero liaison serait un cout sans contrepartie (CLAUDE.md regle 7). Elle vit
dans `mouvement_5_21_bloc_research_test.go`, avec son A/B dans `TestGate516`.
